campus-tokenhub · octafuse-gateway

TokenHub 学校门户 × OctaFuse 网关：技术架构与数据流程

一套七容器全栈：外部 /tokenhub/* 整段交给 Nginx，路径细分全部发生在这一跳； 门户（Next.js）与网关（Proxy / Admin）共用同一个 Postgres，靠 octafuse_gateway 与 portal 两个 schema 做命名空间隔离。 以下四张图按「部署拓扑 → 登录开户 → 推理主链路 → 管理侧写链路」排列。

图 1

技术架构图｜部署拓扑与逻辑分层

五层自上而下：用户 → 接入 → 业务应用（门户） → 网关能力（管理 / 代理） → 数据，右侧为外部依赖。门户是聚合层，单向依赖下面的管理服务。

同步调用 门户 → 网关的依赖调用（向下） 只读 / 跳转 / 异步 / 外围调用 门户（业务聚合） 管理服务 代理服务
  • 部署平级，依赖分上下层。三个容器挂在 Nginx 后面是并列的三条路由，但依赖方向是单向的：门户向下调管理服务的 Admin API，读模型、用户、额度、日志。管理台反过来验签门户的 portal_session（只为人类登录），这是唯一一条反向依赖。
  • 一条没画在主线上的隐式调用。模型集市的数据实际来自代理服务暴露的公开目录 GET /catalog/models（无认证，网关进程内缓存 45 秒）。它不构成业务依赖——推理流量与门户无关——但排查「刚初始化完模型没出现」会踩到：网关 45 秒 + 门户 15 秒两层缓存。
  • 门户不代理推理流量。学生调模型是浏览器 / 终端直连 NEXT_PUBLIC_PROXY_BASE，Key 只在客户端内存，门户只负责下发与吊销。
  • 三路分流的差异有原因：门户是 Next，页面里写的是根绝对路径 /_next/…，反代剥前缀会 404 或抢共享域名的根路径，所以自带 basePath 原样透传；管理台与推理 API 都按根路径运行，剥一次即可。
  • 权限放大点：门户服务端持有网关管理员账密，换 admin_session 后读写全站用户与密钥，进程内做登录单飞避免触发管理台锁定。这是整套架构里唯一需要严格守住的凭证边界。
  • 数据边界：额度、密钥、调用日志、模型目录、初始化状态全部实时读网关，门户不落盘；只有活动配置、管理员名单等业务表 + 配置表落在 portal.*。
  • 部署时序：postgres → migrate（建表 + 种子，跑完退出）→ gateway-proxy / gateway-admin → portal → portal-seed（只填空值，不覆盖设置页改过的配置）→ nginx，前一步健康才起下一步。
图 2

数据流程图｜登录与开户

一次授权码登录要穿过 IdP、门户、网关 Admin API 三段。开户是「get-or-create」语义（external_system + external_user_id 幂等），失败不阻断登录。

  • 门户从不存学生身份。IdP 返回的 sub 只进会话 Cookie；网关侧的用户 ID 由第 ⑨ 步 get-or-create 拿到，也进 Cookie，不落门户库。
  • 开户失败不阻断登录。第 ⑨ 步失败时降级为「账号开通中」，页面提示、审计记 provision.fail，下次登录自动重试。
  • 管理员声明在签发时判定。门户按 portal_shared.admins 名单往会话写 admin: true，管理台每次请求再按当前名单复核，撤权不必等会话过期。
  • 首次部署没有 SSO 时可以用 PORTAL_ADMIN_USERNAME/PASSWORD 走账号密码登录完成对接，AUTH_PROVIDER 配齐后自动关闭。
图 3

数据流程图｜推理调用主链路

这是整套系统真正承压的一条路径：不经过门户，客户端拿着 sk- 直连。鉴权、预算、选路、熔断、failover 全在 proxy 内完成，回包后才异步记账与旁路留存正文。

  • 这条链路完全不经过门户。门户挂了不影响推理；反过来，proxy 挂了门户只能显示「网关不可用」，因为额度、模型目录、日志全是实时读的。
  • 鉴权与预算是同一跳。读 api_keys + users 时顺带做预算周期懒重置并写回，避免额外的定时任务。
  • 路由池是「同款模型」的分流器。deepseek-v4.1-flash-1017 这类跨厂商模型共用一个网关模型 id，各厂商真实模型名写在 route.providerModelName，权重 8:1:1 决定主备倾斜。
  • 记账与正文都在回包之后。记账走异步 sink，正文走攒批队列，两者都不阻塞 token 流；这也是为什么「关闭正文留存」只影响后续调用、不影响计费。
图 4

数据流程图｜初始化与统一采买写入

门户唯一的写网关路径：把统一采买的云厂商 Key、模型清单与路由写成网关的 provider / model / route，写完即生效。其余管理动作一律跳网关管理台。

  • 初始化入口不关闭。再次进入是「重新初始化」：可补选模型、换 Key，完成时间按最后一次重跑刷新，已建的模型不会被删除。
  • 推荐清单是版本化数据。腾讯云在 src/lib/onboarding/presets/tokenhub-<日期>.json，阿里云 / 火山是手写快照，每家都标注官方文档来源。
  • 初始化是门户唯一的写网关路径。其余全部是读：模型目录、额度、日志、正文详情、初始化状态都实时打网关 API。
